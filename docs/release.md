# Releasing the browser extension

One source, three browsers (board #287). A release is a git tag; the
workflow builds Chrome, Firefox and Safari from it, submits Firefox to its
public listing on addons.mozilla.org, uploads the Chrome package to the Web
Store, and puts every package in the Cloudflare R2 bucket behind
**https://app-downloads.zebu.work/extension/**.

## Cutting a release

```bash
scripts/release.sh --dry-run     # rehearse: prints every step, touches nothing
scripts/release.sh               # 0.2.0 -> 0.2.1
scripts/release.sh --minor       # 0.2.0 -> 0.3.0
scripts/release.sh 1.0.0         # exactly that
```

The script refuses a dirty tree, a branch other than `main`, a `main` behind
`origin/main` and a tag that already exists; runs the gate (`npm run build`,
`npm run typecheck`, `npm test`, `npm run i18n:check`,
`scripts/tests/publish-r2.test.sh`); writes the version into `package.json`
and the lockfile; commits `Release X.Y.Z`; tags `vX.Y.Z`; pushes both. The
version lives in `package.json` only: `build.mjs` stamps it into every
browser's manifest, and the workflow's first job refuses a tag that disagrees.

## What the workflow does (`.github/workflows/release.yml`)

| Job | What | Needs |
|---|---|---|
| `verify` | the gate, the release-script tests, tag = package.json | — |
| `build` | `npm run package` → `zebu-{chrome,firefox,safari}-X.Y.Z.zip`; the Firefox build is submitted to the AMO listing and, once Mozilla approves it, fetched back as the signed `.xpi`; the Chrome zip goes to the Web Store | `AMO_*`, `CWS_*` (each optional) |
| `safari` | wraps `dist/safari` with `xcrun safari-web-extension-converter` and attaches the Xcode project as an artifact | a macOS runner |
| `publish` | every package to R2 under the version, aliases under `latest/`, then `latest.json` and Firefox's `updates.json` last, read back over the public hostname | `R2_*` (required) |

`workflow_dispatch` runs the same build and publish into
`extension/_dryrun/<run id>/` and skips the stores: a rehearsal of the
credentials, the endpoint, the bucket permissions and the ordering.

## How each browser updates

- **Chrome** updates only from the Chrome Web Store (self-hosted `.crx`
  auto-update is blocked for normal users). The R2 copy is the archive and
  the *load unpacked* source.
- **Firefox** updates from its public listing,
  **https://addons.mozilla.org/firefox/addon/zebu-time-tracking/**, the way
  every listed add-on does: Firefox asks AMO for new versions of the gecko
  id `extension@zebu.work`. The manifest carries no `update_url` (AMO's
  linter refuses one in a listed package). Copies installed from our bucket
  before the listing existed are bridged over by `updates.json`; see the
  next section.
- **Safari** is the same code wrapped in a macOS app. The workflow produces
  the Xcode project; building, signing and App Store submission are not
  automated yet (see below).

## Firefox: the listing, the review, and the copies installed before it

Every tag submits the Firefox build to the **listed** channel with
`web-ext sign --channel listed --amo-metadata amo/listing.json
--upload-source-code source.zip --approval-timeout 0`:

- `amo/listing.json` is the listing (name, summary in the eleven locales,
  description, categories, homepage, support URL, license, notes for the
  reviewers). It is generated by `scripts/amo-listing.mjs` from
  `_locales/*/messages.json` and `scripts/listing-captions.json` and checked
  by `tests/amo.test.ts`; after changing the store description, run
  `node scripts/amo-listing.mjs --write`. The slug (the listing URL) and the
  license are constants at the top of that script. AMO takes these fields
  from the request on every submission, not from the manifest, so the repo
  is the source of truth for the listing.
- `amo/privacy-policy.md` is set on the listing right after the submission
  (`scripts/amo.mjs set-policy`); AMO requires a privacy policy of an
  extension that sends data anywhere.
- The source archive is `git archive` of the tag: the package is minified,
  so Mozilla's reviewers rebuild it from source (README, *Reproducing a
  build*).

A listed version is signed only after Mozilla's review, which takes
minutes when the automatic review passes and days when a human looks. The
job therefore does not block on it: `scripts/amo.mjs await-signed` polls for
up to `AMO_APPROVAL_WAIT` seconds (15 minutes) and the release goes on
either way.

- **Approved in time:** the signed `.xpi` joins the packages,
  `latest.json` serves it, and `extension/firefox/updates.json` names it.
- **Review still open:** the release ships the Firefox source zip, the
  listing link is in `latest.json` regardless, and `updates.json` is left
  exactly as it was. Once AMO approves the version, **re-run the release
  workflow** (*Re-run all jobs* on the run): the Firefox step finds the
  version on AMO, submits nothing, downloads the signed file, the Chrome
  step sees the Web Store already holds the version and skips, and the
  publish job writes the `.xpi` and the new `updates.json`.

**Copies installed from our bucket before the listing** (every install
until this switch) have a manifest that names
`https://app-downloads.zebu.work/extension/firefox/updates.json`, and
Firefox keeps checking the `update_url` of the version it has installed.
That file therefore stays, and it keeps pointing at signed builds: from now
on the *listed* `.xpi` copied to R2 (same bytes Mozilla serves; a listed
signature installs from anywhere). A copy that installs it no longer has an
`update_url`, so from then on Firefox updates it from AMO like a store
install. Every self-hosted copy makes that hop exactly once, at the first
listed version that reaches `updates.json`; a copy that missed several
releases still hops at its next check, since `updates.json` only ever
names a signed listed build. Nothing has to be timed, and nothing about
the unlisted channel is used any more.

## Secrets on the repository

| Secret | Required | Used for |
|---|---|---|
| `R2_ACCOUNT_ID`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY` | yes | publishing to `app-downloads.zebu.work` (the desktop repository's token works: same bucket) |
| `AMO_JWT_ISSUER`, `AMO_JWT_SECRET` | for the Firefox listing | addons.mozilla.org → Tools → *Manage API keys*; the same key that signed the unlisted builds |
| `CWS_CLIENT_ID`, `CWS_CLIENT_SECRET`, `CWS_REFRESH_TOKEN`, `CWS_EXTENSION_ID` | for the Web Store upload | a Google Cloud OAuth client with the *Chrome Web Store API* enabled; the refresh token from one consent flow; the extension id after the first manual upload |
| `APPLE_TEAM_ID` | Safari, later | the converter's bundle id is `work.zebu.extension` |

Without `AMO_*` the release ships `zebu-firefox-X.Y.Z.zip` (source), nothing
reaches AMO and `updates.json` is untouched; without `CWS_*` the Chrome zip
is only archived on R2. Both cases are warnings in the workflow, not
failures, so the first releases can go out before the store accounts exist.

## The bucket layout

```
extension/
  latest.json                   { version, pub_date, builds: { chrome, firefox, safari } }, each with
                                its store link (chrome: Web Store, firefox: the AMO listing)
  firefox/updates.json          Firefox's update manifest for the copies installed from here before
                                the AMO listing (gecko id → versioned listed xpi + sha256)
  latest/zebu-chrome.zip        aliases the downloads page links to; each downloads
  latest/zebu-firefox.xpi       under its versioned name (Content-Disposition)
  latest/zebu-safari.zip
  0.3.0/zebu-chrome-0.3.0.zip   every build, kept forever, immutable
  0.3.0/zebu-firefox-0.3.0.xpi
  0.3.0/zebu-safari-0.3.0.zip
  _dryrun/<run id>/…            rehearsals; expired by a lifecycle rule
```

Every URL in `latest.json` and `updates.json` points into the immutable
per-version prefix, never at an alias (`scripts/extension-manifest.mjs`
enforces it). Nothing in the workflow deletes; `scripts/publish-r2.sh`
uploads object by object and reads each back.

## Safari, when the Apple side is confirmed

1. `npm run build:safari && xcrun safari-web-extension-converter dist/safari
   --app-name Zebu --bundle-identifier work.zebu.extension --macos-only`
2. Open the project in Xcode, set the team, archive, upload to App Store
   Connect (or distribute with a Developer ID for direct download).
3. Safari has no idle API and no extension notifications; the build asks for
   neither permission and hides the idle card (`src/platform.ts`).

## Not automated

- The Chrome Web Store review, and the first listing (a manual upload that
  yields `CWS_EXTENSION_ID`).
- Mozilla's review of each listed Firefox version, and on the AMO listing
  the parts the API does not carry: the icon, the screenshots
  (`listing/en/*.jpg` fit), and confirming the slug and the license after
  the first submission (developer hub → the add-on → *Edit Product Page*).
- The Safari archive and App Store submission.
- The downloads page in `zebu-public` links the `latest/` aliases, so it does
  not change per release; only the copy (browser minimums) does.
